## 系统架构概览

### 整体架构
该系统采用**前后端分离 + WebSocket实时通信**的架构，实现客服与用户之间的即时消息通知。

**技术栈：**
- 后端：Spring Boot + Jakarta WebSocket
- 前端：Vue.js (客服端) + 原生JavaScript (游客端)
- 实时通信：WebSocket
- 数据存储：MySQL + Redis
- 多租户：基于appid的租户隔离

### 核心设计理念
1. **多租户隔离**：每个租户(appid)拥有独立的客服和用户空间
2. **实时双向通信**：基于WebSocket实现毫秒级消息推送
3. **在线状态管理**：实时跟踪客服和用户的在线状态
4. **会话持久化**：消息和会话记录持久化到数据库
5. **分布式支持**：通过Redis存储会话元数据，支持多节点部署

## 核心组件分析

### 1. WebSocket服务层

#### ChatWebSocketServer
**位置：** `io.renren.crmchat.websocket.ChatWebSocketServer`

**职责：**
- WebSocket连接的生命周期管理（onOpen, onMessage, onClose, onError）
- 客户端认证和会话注册
- 消息路由和分发
- 心跳保持

**关键方法：**
```java
@OnOpen
public void onOpen(Session session)
// 1. 解析URL参数（type, token, appid）
// 2. 调用认证处理器验证身份
// 3. 注册会话到SessionRegistry
// 4. 更新数据库在线状态
// 5. 发送login/success/ping消息

@OnMessage
public void onMessage(Session session, String message)
// 处理客户端消息：ping, user, logout, online, to_chat, open, set_form_type

@OnClose
public void onClose(Session session)
// 1. 从SessionRegistry移除会话
// 2. 更新数据库离线状态
// 3. 广播用户离线消息

static void broadcast(String appid, int userId, String type, Object payload)
// 向指定用户的所有WebSocket会话推送消息
```

#### WebSocketSessionRegistry
**位置：** `io.renren.crmchat.websocket.WebSocketSessionRegistry`

**职责：**
- 内存中维护所有活跃的WebSocket会话
- 提供按appid+userId查询会话的能力
- 支持按用户类型(kefu/user/admin)查询
- 会话元数据持久化到Redis（支持分布式）

**核心数据结构：**
```java
// 按 appid::userId 索引的会话集合
ConcurrentHashMap<String, CopyOnWriteArraySet<SessionHolder>> SESSIONS

// 按 Session 对象索引的会话持有者
ConcurrentHashMap<Session, SessionHolder> SESSION_LOOKUP

// 会话持有者，包含：
class SessionHolder {
    Session session;           // WebSocket会话
    String appid;              // 租户ID
    int userId;                // 用户ID
    String userType;           // 用户类型：kefu/user/admin
    Integer currentTargetUserId; // 当前聊天对象
    Integer formType;          // 表单类型
    boolean tourist;           // 是否游客
    Integer serviceId;         // 客服ID（仅客服类型）
}
```

**关键方法：**
```java
// 注册会话
static SessionHolder register(Session session, String appid, int userId, ...)

// 查询指定用户的所有会话
static Set<SessionHolder> getSessions(String appid, int userId)

// 查询指定类型的所有会话（如所有客服）
static Set<SessionHolder> getSessionsByType(String appid, String userType)

// 检查用户是否在线
static boolean isOnline(String appid, int userId)

// 检查用户是否正在与某人聊天
static boolean isEngaged(String appid, int userId, int targetUserId)

// 更新会话的userId（用于游客身份确认）
static void updateUserId(Session session, int newUserId)
```

#### WebSocketPushService
**位置：** `io.renren.crmchat.websocket.WebSocketPushService`

**职责：**
- 提供高层次的消息推送API
- 封装不同类型的消息推送逻辑
- 处理消息序列化和异常

**核心方法：**
```java

boolean isOnline(String appid, int userId)

// 发送聊天消息（游客发送）
```

### 2. 认证处理层

#### AuthHandlerFactory
**位置：** `io.renren.crmchat.websocket.handler.AuthHandlerFactory`

**职责：**
- 根据用户类型(type参数)返回对应的认证处理器
- 支持：user(游客), kefu(客服), admin(管理员), tenant(租户)

#### UserHandler (游客认证)
**关键逻辑：**
1. 验证JWT token
2. 从token中提取userId和appid
3. 查询chat_user表验证用户存在
4. 处理游客身份同步（user消息）

#### KefuHandler (客服认证)
**关键逻辑：**
1. 验证JWT token
2. 从token中提取serviceId(客服ID)和appid
3. 查询chat_service表验证客服存在且启用
4. 返回客服的user_id（用于消息记录）

### 3. 业务服务层

#### MobileServiceService (游客消息服务)
**位置：** `io.renren.crmchat.service.MobileServiceService`

**核心方法：sendMessage**
```java
@Transactional
public Map<String, Object> sendMessage(Map<String, Object> data, String appid)
```

**业务流程：**
1. 验证参数：to_user_id, msn, guid, user_id
2. 验证不能和自己聊天
3. 查询客服信息
4. 保存消息到`eb_chat_service_dialogue_record`表
5. 更新会话记录到`eb_chat_service_record`表
6. **先广播用户上线消息**（避免竞态条件）
7. 延迟100ms确保消息顺序
8. 如果客服在线，推送reply消息
9. 返回消息记录

**关键修复：**
```java
// ⭐ 先广播用户上线消息,确保客服端左侧列表有该用户
webSocketPushService.broadcastUserStatus(appid, userId, 1, nickname, avatar);

// 短暂延迟(100ms),确保客服端先处理user_online消息
Thread.sleep(100);

// 再发送消息内容
if (webSocketPushService.isOnline(appid, toUserId)) {
    webSocketPushService.sendReply(appid, toUserId, response);
}
```

#### KefuMessageService (客服消息服务)
**位置：** `io.renren.crmchat.service.KefuMessageService`

**核心方法：sendMessage**
```java
@Transactional
public Map<String, Object> sendMessage(Map<String, Object> data, Integer kefuUserId, String appid)
```

**业务流程：**
1. 验证参数：to_user_id, msn, guid
2. 查询客服信息
3. 保存消息到`eb_chat_service_dialogue_record`表
4. 更新两条会话记录：
   - 游客的会话记录：user_id=游客, to_user_id=客服
   - 客服的会话记录：user_id=客服, to_user_id=游客
5. 检查游客在线状态
6. 如果游客在线，推送reply消息；否则推送mssage_num
7. 更新徽章通知
8. 返回消息记录

**数据库设计理解：**
```
eb_chat_service_record 表设计：
- 每个会话有两条记录（双向）
- 游客视角：user_id=游客ID, to_user_id=客服user_id
- 客服视角：user_id=客服user_id, to_user_id=游客ID
- 这样双方都能查询到自己的会话列表
```

## 消息通知流程

### 场景1：游客发送消息给客服

```
1. 游客前端 → POST /api/mobile/service/message
   ↓
2. MobileServiceService.sendMessage()
   ↓
3. 保存消息到数据库
   ↓
4. 广播用户上线状态给所有客服
   webSocketPushService.broadcastUserStatus()
   → 遍历所有客服session
   → 发送 type: user_online 消息
   ↓
5. 延迟100ms（确保消息顺序）
   ↓
6. 检查客服是否在线
   webSocketPushService.isOnline(appid, kefuUserId)
   ↓
7. 如果在线，推送消息内容
   webSocketPushService.sendReply()
   → 发送 type: reply 消息
   ↓
8. 返回结果给游客前端
   ↓
9. 游客前端乐观更新UI
```

**WebSocket消息格式：**
```json
// user_online 消息
{
  "type": "user_online",
  "data": {
    "user_id": 123,
    "online": 1,
    "nickname": "游客_abc",
    "avatar": "http://..."
  }
}

// reply 消息
{
  "type": "reply",
  "data": {
    "id": 456,
    "user_id": 123,
    "to_user_id": 789,
    "msn": "你好，我需要帮助",
    "msn_type": 1,
    "nickname": "游客_abc",
    "avatar": "http://...",
    "add_time": 1234567890,
    "guid": "unique-message-id"
  }
}
```

### 场景2：客服回复游客

```
1. 客服前端 → POST /api/kefu/message/send
   ↓
2. KefuMessageService.sendMessage()
   ↓
3. 保存消息到数据库
   ↓
4. 更新两条会话记录（游客和客服）
   ↓
5. 检查游客是否在线
   webSocketPushService.isOnline(appid, visitorUserId)
   ↓
6a. 如果游客在线
    → webSocketPushService.sendReply()
    → 发送 type: reply 消息
    → 游客实时收到消息
   ↓
6b. 如果游客离线
    → webSocketPushService.sendMessageNum()
    → 发送 type: mssage_num 消息
    → 游客下次连接时收到未读数
   ↓
7. 更新徽章通知
   autoBadgeService.dispatch()
   ↓
8. 返回结果给客服前端
   ↓
9. 客服前端乐观更新UI
```

### 场景3：客服转接

```
1. 客服A → POST /api/kefu/chat/transfer
   {kefuToUserId: 客服B的user_id, chatUserId: 游客ID}
   ↓
2. KefuChatService.transferService()
   ↓
3. 事务操作：
   - 查询原会话记录
   - 为客服B创建新会话记录
   - 删除客服A的会话记录
   - 保存转接关系到辅助表
   ↓
4. 发送WebSocket通知：
   - 给客服B：type: transfer（新增会话）
   - 给客服A：type: rm_transfer（移除会话）
   - 给游客：type: to_transfer（转接通知）
   ↓
5. 更新双方徽章通知
```

## WebSocket通信机制

### 连接建立流程

```
1. 客户端发起连接
   ws://host:port/ws?type=user&token=xxx&appid=xxx
   ↓
2. ChatWebSocketServer.onOpen()
   ↓
3. 解析URL参数
   - type: user/kefu/admin/tenant
   - token: JWT token
   - appid: 租户ID（可选，优先从token提取）
   ↓
4. 认证
   AuthHandlerFactory.getHandler(type)
   → UserHandler/KefuHandler/AdminHandler
   → 验证token
   → 查询数据库验证用户
   → 返回SessionIdentity
   ↓
5. 注册会话
   WebSocketSessionRegistry.register()
   → 存入内存Map
   → 持久化到Redis
   ↓
6. 更新在线状态
   markUserOnline()
   → 更新chat_user.online = 1
   → 更新chat_service.online = 1（如果是客服）
   → 更新chat_service_record.online = 1
   ↓
7. 发送登录成功消息
   sendEnvelope(session, "login", {...})
   sendEnvelope(session, "success", {...})
   sendEnvelope(session, "ping", {...})
```

### 心跳机制

**客户端 → 服务端：**
```json
{"type": "ping"}
```

**服务端 → 客户端：**
```json
{
  "type": "pong",
  "data": {
    "timestamp": 1234567890
  }
}
```

**作用：**
- 保持连接活跃
- 刷新Redis会话TTL（120秒）
- 检测连接断开

### 消息类型汇总

| 消息类型 | 方向 | 说明 |
|---------|------|------|
| login | S→C | 登录成功 |
| success | S→C | 连接成功 |
| ping | C→S | 心跳请求 |
| pong | S→C | 心跳响应 |
| user | C→S | 游客身份同步 |
| chat | S→C | 游客发送的消息 |
| reply | S→C | 客服回复的消息 |
| mssage_num | S→C | 未读消息数通知 |
| user_online | S→C | 用户上线通知（广播给客服） |
| online | C→S/S→C | 在线状态变更 |
| to_chat | C→S | 切换聊天对象 |
| open | C→S | 打开对话 |
| logout | C→S | 退出登录 |
| transfer | S→C | 客服转接（新增会话） |
| rm_transfer | S→C | 移除转接会话 |
| to_transfer | S→C | 转接通知用户 |

## 关键技术实现

### 1. 多租户隔离

**实现方式：**
- 每个WebSocket连接携带appid
- SessionRegistry按 `appid::userId` 索引
- 消息推送时严格校验appid
- 数据库查询都带appid条件

**代码示例：**
```java
// 查询会话时的appid隔离
private static String key(String appid, int userId) {
    return appid + "::" + userId;
}

// 广播消息时的appid过滤
public static Set<SessionHolder> getSessionsByType(String appid, String userType) {
    Set<SessionHolder> result = new CopyOnWriteArraySet<>();
    for (Set<SessionHolder> holders : SESSIONS.values()) {
        for (SessionHolder holder : holders) {
            if (appid.equals(holder.getAppid()) && userType.equals(holder.getUserType())) {
                result.add(holder);
            }
        }
    }
    return result;
}
```

### 2. 会话状态管理

**在线状态更新：**
```java
private static void markUserOnline(SessionHolder holder, boolean online) {
    int flag = online ? 1 : 0;
    
    // 1. 更新chat_user表
    chatUserMapper.update(
        new ChatUserEntity().setOnline(flag),
        new UpdateWrapper<>().eq("appid", appid).eq("id", userId)
    );
    
    // 2. 更新chat_service表（如果是客服）
    if ("kefu".equals(userType)) {
        chatServiceMapper.update(
            new ChatServiceEntity().setOnline(flag).setIsBackstage(flag),
            wrapper
        );
    }
    
    // 3. 更新chat_service_record表
    chatServiceRecordMapper.update(
        new ChatServiceRecordEntity().setOnline(flag),
        wrapper
    );
    
    // 4. 广播状态变更（如果是游客）
    if ("user".equals(userType)) {
        pushService.broadcastUserStatus(appid, userId, flag, nickname, avatar);
    }
}
```

**注意：** 更新在线状态时**不应该**修改`update_time`字段，否则会导致刷新页面时会话列表时间变化。

### 3. 消息去重机制

**问题：** 游客发送消息后，前端乐观更新UI，如果再收到WebSocket推送的同一条消息，会重复显示。

**解决方案：**
```javascript
// 前端维护已发送消息的guid集合
const sentMessageGuids = new Set();

// 发送消息时记录guid
function sendMessage(message) {
    const guid = generateGuid();
    sentMessageGuids.add(guid);
    // ... 发送消息
}

// 收到WebSocket消息时检查
ws.onmessage = function(event) {
    const message = JSON.parse(event.data);
    if (message.type === 'reply' && message.data.guid) {
        if (sentMessageGuids.has(message.data.guid)) {
            console.log('跳过重复消息:', message.data.guid);
            sentMessageGuids.delete(message.data.guid);
            return;
        }
    }
    // ... 处理消息
}
```

### 4. 竞态条件处理

**问题：** 首次游客发消息时，客服端可能先收到`reply`消息，但左侧用户列表还没有该用户，导致消息无法显示。

**解决方案：**
```java
// 1. 先广播用户上线消息
webSocketPushService.broadcastUserStatus(appid, userId, 1, nickname, avatar);

// 2. 延迟100ms确保客服端先处理user_online消息
Thread.sleep(100);

// 3. 再发送消息内容
webSocketPushService.sendReply(appid, toUserId, response);
```

这样确保客服端：
1. 先收到`user_online`消息，更新左侧用户列表
2. 再收到`reply`消息，能找到对应的会话并显示

## 已修复的问题

### 1. 游客消息发送者显示错误

**问题：** 游客发送的消息在游客端显示为客服发送。

**原因：** 前端判断消息发送者时，WebSocket消息和HTTP响应的数据结构不一致。

**修复：**
```javascript
// 修复前：只比较user_id
let isUser = (msg.user_id === userId);

// 修复后：区分WebSocket消息和乐观更新
let isUser;
if (msg.user_id !== undefined) {
    // WebSocket消息 - 比较user_id
    isUser = userId && (msg.user_id === userId);
} else {
    // 乐观更新 - 一定是用户自己发的
    isUser = true;
}
```

### 2. 客服端实时接收问题

**问题：** 游客发送消息后，客服端需要刷新才能看到。

**原因：** 后端检查`isEngaged`（客服是否正在查看该对话），未engaged时只发送`mssage_num`通知，不发送实际消息内容。

**修复：**
```java
// 修复前：
if (isEngaged) {
    webSocketPushService.sendReply(...);
} else {
    webSocketPushService.sendMessageNum(...);
}

// 修复后：客服在线时总是发送实际消息内容
if (webSocketPushService.isOnline(appid, toUserId)) {
    webSocketPushService.sendReply(appid, toUserId, response);
}
```

### 3. 首次游客发消息竞态问题

**问题：** 首次游客发消息时，客服端收到`reply`但左侧列表还没有该用户。

**修复：** 见"竞态条件处理"章节。

### 4. 退出登录WebSocket未关闭

**问题：** 客服点击退出登录后，WebSocket连接未关闭，导致在线状态未更新。

**修复：**
```javascript
// 前端添加manualClose标志
this.manualClose = false;

// 退出登录时
logout() {
    this.manualClose = true;  // 标记为手动关闭
    this.ws.close();
}

// onclose事件中检查
ws.onclose = function() {
    if (!this.manualClose) {
        // 非手动关闭，尝试重连
        reconnect();
    }
}
```

## 性能优化建议

### 1. 消息批量推送
当前每条消息都单独推送，可以考虑批量推送：
```java
// 收集一段时间内的消息
List<Message> batch = new ArrayList<>();
// 定时或达到阈值后批量推送
webSocketPushService.sendBatch(appid, userId, batch);
```

### 2. Redis缓存优化
- 缓存在线客服列表（避免频繁查询数据库）
- 缓存用户信息（nickname, avatar）
- 设置合理的TTL

### 3. 数据库索引优化
确保以下字段有索引：
- `eb_chat_service_record`: (appid, user_id), (appid, to_user_id)
- `eb_chat_service_dialogue_record`: (appid, user_id, to_user_id)
- `eb_chat_user`: (appid, id), (appid, online)
- `eb_chat_service`: (appid, user_id), (appid, online)

### 4. 分布式部署支持
当前已支持Redis存储会话元数据，但消息推送仍是本地内存：
- 考虑使用Redis Pub/Sub实现跨节点消息推送
- 或使用消息队列（RabbitMQ/Kafka）
